# 投稿の日誌

> **先に [`../../CLAUDE.md`](../../CLAUDE.md) の「YouTube 投稿の恒久指令」を読むこと。**
> 目標（総再生数の成長率の最大化）と、たった3つの制約はそこにある。この日誌が
> 持っているのは「なぜそうしたか」だけで、**何を目指しているかは持っていない。**
> 日誌の記述が指令と食い違ったら、指令が勝つ。

**追記だけ。過去の行を書き換えないこと。**

毎日の投稿は、常駐セッションに定期実行が撃ち込まれる形で回っています。そのセッションは
永遠には続きません。文脈が伸びれば要約されて薄れますし、いつか別のセッションに引き継ぐ
ことになります。

そのとき失われるのはコードではなく**判断の理由**です。何を試して効かなかったのか、
なぜその切り口をやめたのか、いつ何を変えたのか。`posted.json` は「何をいつ出したか」
しか持たず、アナリティクスは「どうなったか」しか持ちません。**「なぜそうしたか」を
持つ場所がここです。**

## 書き方

1回の投稿につき数行。長さより、書いてあること。**見出しに自分のセッションIDを
書いてください**（システムプロンプトの Claude-Session の URL にあります）。

```
## 2026-08-04  (session_01AbCdEf...)
- …
```

書く価値があるのは、**数字を見ても分からないこと**だけです。何を出したかは
`posted.json` に、成績はアナリティクスにあります。ここに要るのは、その数字を見て
何を考え、何を変え、何を変えなかったか。変えなかった理由のほうが、しばしば有用です。

**読むのは末尾10件ほどで足ります。** このファイルは伸び続けるので、全部読む必要は
ありません。古い記入が要るのは、いま触っている箇所の経緯を辿るときだけです。

## 毎回、必ず読み直すこと

**前回の記憶で動かないでください。** 同じセッションに撃ち込まれ続けるので、
「昨日これをやった」という感覚は残っています。その感覚は、日が経つほど薄れていく
一方で、薄れたことには気づけません。

だから毎回、このファイルと `posted.json` とアナリティクスを読み直してから判断して
ください。**1回の実行が独立していれば、このセッションは伸び続けても構いません。**
文脈が要約されて古い実行記録が消えても、失われるのはログの見た目であって、
判断材料ではないからです。

逆に言えば、読まずに記憶で動いた時点でこの前提が崩れます。乗り換えても直りません
——— 新しいセッションでも同じことをするので。壊れる経路はここ一本です。

## 引き継ぐとき

乗り換えは、伸びたからではなく **セッションが落ちたとき** か、**別の環境に移すとき**
にだけ必要になります。そのときは最後の記入を厚めにしてください。次に来る側は、この
ファイルと `posted.json` とアナリティクスしか持っていません。手順は
[`KICKOFF.md`](KICKOFF.md) にあります。

## 2026-08-10 13:00 JST —— サンプラーの push が毎回落ちていた（detached HEAD）

**症状**: `snapshot.mjs --rate` の末尾で
`The destination you provided is not a full refname` が出て、
`views.jsonl の自動コミットに失敗` で終わっていた。preflight は

**原因**: **子セッションの checkout は detached HEAD。** 枝の先端と同じコミットに
いるだけで、枝には乗っていない。だから

- `git push origin HEAD` は push 先の枝名を解決できずに落ちる
- `git branch --show-current` が空なので、preflight の `origin/` も `?` になる

**何が失われていたか**: サンプルのコミット（f608e9f）が**コンテナの中だけに
在って push されていなかった。** コンテナは毎時作り直されるので、
**気づかなければ黙って消えていた。** 今回は手で
`git push origin HEAD:refs/heads/<枝>` して回収した。

**直したもの（印字ではなく、動く側を直した）**:

- `snapshot.mjs` —— `targetBranch()` を足し、`HEAD:refs/heads/<枝>` を明示して push する。
  detached のときは「**HEAD がその子孫になっている唯一のローカル枝**」を枝とみなす
  （checkout 元の枝がそれ）。**候補が0でも2以上でも例外を投げる** ——
  枝を推測して push するくらいなら落ちるほうがいい
- `preflight.sh` —— 同じ解決を入れ、`git 枝 :` の行を足した。
  以前は毎回「ズレている」と出ていたが、**実際にズレているのか枝名が引けないだけかを
  区別していなかった。** 出ない警告より、**理由の分からない警告のほうが悪い**
  ——— 4回以上「ズレている」を読んで、毎回無視していた

**棄却した直し方**: `git checkout -B <枝>` で枝に乗せ直すのが本筋だが、
**この環境の承認分類器が checkout も `update-ref`+`symbolic-ref` も止める。**
人の承認を待つ形になるので（指示8）**採らない。**
**detached のままでも正しく動く形**に寄せた ——— 承認の要らない `push` の
refspec だけで済む。**環境が直っても、この形は壊れない。**

**見直す条件**: 他にも `git ... HEAD` を暗黙に枝と見なしている箇所があれば同じ穴。
いま grep した限りでは push はここ1か所だけ。**新しく push を書くときは
必ず refspec を明示すること。**

### 待機ループが自分自身を待っていた（セッション中ずっと）

撮影の完了を待つのにこう書いていた：

    until ! pgrep -f 'autopost.mjs' >/dev/null; do sleep 5; done

**この待機シェル自身のコマンド行に `autopost.mjs` が入っている**ので、`pgrep` が
自分に一致して**永久に終わらない**。12個たまっていた。撮影はとっくに終わっていて、
気づいていなかったのは待機側だけ。「まだ撮影中」と何度も報告したのはこれ。

正しい書き方は、`node` の起動に限定するか、パターンを自己一致しない形にする：

    until ! pgrep -f 'node .*autopost.*\.mjs' >/dev/null; do sleep 5; done
    # あるいは pgrep -f '[a]utopost\.mjs' （角括弧で自分に一致させない）

**そもそも待つ必要が薄い。** バックグラウンドで投げたコマンドは完了時に通知が
来るので、待機ループを別に立てるのは二重で、しかもこの罠を踏む。

### Cloud TTS は同じ入力でも尺が3割ぶれる（尺合わせを作り直した）

`keep` を撮っていて見つけた。**同じ文・同じ speakingRate** で、

    1回目  2.28秒
    2回目  3.07秒   ← 35%長い

open_jtalk は決定的だったので、尺合わせは「1回測って、1回だけ速度を直す」形で
足りていた。**Cloud TTS ではそれが破れる。** 1回目の計測から計算した補正は、
2回目の合成には当てはまらない。

**いちばん切れやすいのは最後の行**＝テスター募集の案内。動画の存在理由が、
たまたまその日ぶれた合成のせいで途中で消える経路だった。

直し方は「予測」から「収束」へ。**調整→測り直し→繰り返し**（最大3回、4%の余裕つき）。
上限は据え置き —— 上限は聞ける速さの限界であって、そもそも長すぎる行を救う速度は
無い。収まらない行は警告を出し、台本を短くする。

**教訓の形**: 決定的なものを非決定的なものに差し替えたとき、**その決定性に
乗っていた仕組みが黙って壊れる。** 声を差し替えたときに尺合わせを見直すべきだった。

### 「時間帯が効く」の対抗仮説：初期ブーストが尽きただけ

    順2  08-03 12:27   768    早い & 良い時間帯
    順3  08-03 21:00     1    遅い & 悪い時間帯

    順5  08-04 14:00     0
    順6  08-04 17:40     1

**同じデータが完全に説明できる。** 私が「09〜13時台が効く」と書いたのは、

- 初期ブーストモデル → **時刻をどういじっても無駄。** 配信は視聴維持で勝ち取るもので、

どちらも「最初期」ではない。

- 両方沈んだ → **初期ブーストモデル。** 時刻の話は全部捨てて、維持率と継続に寄せる
- 片方だけ → 形式（短縮版 vs 従来版）の差。時間帯モデルは弱まる

**この節を読まずに明日の数字を見ないこと。** 「12時台は2/2で強い」という

### 主張の裏付けを囲む `__spot` を入れた（判定の壊れ方も見つけた）

`overlay.js` に `__spot(セレクタ, ms)` を足した。生きている要素の位置を測って
金色の枠で囲む。`endless` の掴みで「第52層」のバッジを囲むよう指定し、
**2.6秒のフレームで出ていることを絵で確認した。**

ゲームは層の数も倍率も HUD の端に小さく描くので、テロップが数字を主張しても
気づかれない。**「嘘ではない」と「伝わる」は別の水準**で、これは後者を上げる部品。
研究の倍率・素材の個数・レシピ数など、他の切り口にも同じ手が使える。

**そして判定が壊れていた。** director 側でこう書いていた：

    const hit = await ev(sel => window.__spot(sel, 2600), sel);
    console.log(hit ? 'ok' : '見つからない');

`ev()` はページ内で例外が出ると**エラー文字列を返す**。文字列は truthy なので、
**あらゆる失敗が「ok」と報告される。** 実際、最初のフレームで囲みが見つからず
「ok と出ているのに映っていない」状態から追いかけることになった。
`=== true` で比べるよう直した。

**教訓**: 真偽を返す関数の結果を truthy で判定しない。失敗が別の型で返る経路が
あるなら、成功の値そのものと比べること。**「ok」と言い張る検査は、検査が無いより悪い。**

### `__spot` の効きは、囲む対象の大きさで決まる

3切り口に付けて絵で確認した。**効き方がはっきり違う。**

- `endless` → `.quotaStageBadge`（第52層・小さいバッジ）。**一点に視線が集まる。**
  これが狙いどおりの使い方
- `idle-trap` → `#quotaBox`（ノルマ帯・画面幅いっぱい）。枠は出るが、
  **「指し示す」ではなく「縁取り」に見える。** 嘘ではないし視線は帯へ寄るが、
  小さいバッジのときのような効果は無い

**対象が大きいほど、囲みは意味を失う。** 画面の大半を囲めば、それは何も指していない
のと同じ。小さくて見落とされる表示にこそ効く道具だと分かった。

囲む対象が**そもそも無い**切り口もある（`recipes` の486、`tree` の71 は画面に数字が
出ない）。ここは別の手が要る —— 数を主張するなら、**数えられるものを画面に出す**
必要がある。

### `pgrep -f` の自己一致、3度目

「撮影中なら新しい撮影を始めない」の見張りが、**自分自身を数えて**いた。今回は
待機ループではなく**前景のコマンド**で、そのシェルのコマンド行に
`node youtube/autopost.mjs ...` という文字列が含まれるため、
`pgrep -f '[n]ode .*autopost'` が自分に一致して「撮影中」と誤報し、
**撮影が黙って飛ばされた**（出力は「撮影中」の1行だけ）。

角括弧（`[n]ode`）は grep 自身の一致は防ぐが、**呼び出し元のシェルには効かない。**

    誤: pgrep -f '[n]ode .*autopost'     ← 自分のラッパーに一致する
    正: pgrep -x node                     ← プロセス名で照合。シェルは bash なので拾わない

**同じ罠を3回踏んだ**（待機ループ12個、ティッカーの見張り、今回）。
文字列で自プロセスを探す限り、書き方を変えても再発する。**プロセス名で照合すること。**

### 新しい切り口 `beyond` —— 単位が尽きた先

`unit`（768回）が当たった理由を「数字が大きい」ではなく **「知っているようで
置き場所の分からない単位」** と読んで、その一段上を作った。

`play.html` の `generateHugeUnit()` を切り出して**実際に走らせて**確かめた数字：

- `JAPANESE_NUMBER_UNITS` の名前付き単位は **17個**（万〜無量大数）
- **無量大数 = 10^68**（level 17 × 4桁）
- level 18 = **10^72 → 「火炉」**。辞書に無い。**ゲームが組み立てた名前**
- 華厳経の実在大数16個（無辺〜不可説不可説転）も、本来の桁位置にだけ入る
- level 18〜200017 で **異なり40,821通り**

テロップで言い切るのは最初の3つだけにした。生成のしくみは説明欄に回す。
**配列の長さを数えず、ゲームのコードを走らせて確かめた** —— `EQUIPMENT=7` /
`STAGES=5` を配列長で誤読した件と同じ轍を踏まないため。

`__spot` は**使わなかった。** 単位名は小さくて見落とされる＝囲みが効く条件だが、
`#cookies` は画面幅いっぱいで、`idle-trap` で「囲みではなく縁取りに見える」と
結論した形そのもの。**自分が出した結論を、都合が悪いから曲げないこと。**
読めなければ直し方は「テロップに引用する」であって「囲む」ではない。

切り口が本体を指定できるようにした（`variants.mjs` の `body`）。
「無量大数の上、あります?」の直後にモンスター狩りが始まっては、問いを立てて
話題を変えているだけになる。`--body` を明示すれば従来どおり上書きできる。

### 仮説: 掴みが「問い」か「言い切り」か

配信された Short 4本を掴みの**形**で並べると、こう分かれる。

| 切り口 | 掴みの形 | バナー | 再生 |
|---|---|---|---|
| unit | **問い** | “正”って単位、知ってます? | **768** |
| （初回） | 募集の告知 | テスター募集 | 208 |
| idle-trap | 言い切り | 放置ゲーの話です | 2 |
| recipes | 言い切り | クリッカーのはずなんですが | 1 |

**問いは1本しかないので、これは所見ではなく仮説。** ただし筋は通る ——
問いは視聴者の頭の中に**答えられない穴**を作る。「正って知ってます?」は
知らないと分かった瞬間に答えが要る。「レシピが486種類あります」は、
まだそのゲームに興味の無い相手には**答える必要のない情報**でしかない。

**検証の段取りは既に組まれている**（追加の投稿を要さない）:

- 8/4 21:30 `endless`（言い切り）
- 8/5 09:30 `tree`（言い切り）、12:20 `boss`（言い切り）
- 8/6 `beyond`（**問い**）—— これが再現テスト

言い切り3本がそろって0〜2回で、`beyond` が伸びれば、形が効いていることになる。
`beyond` も0回なら、`unit` の768回は**形ではなく運**だった可能性が上がる。

**結論を出す前に投稿の形を全部「問い」に揃えないこと。** 対照が消える。
未使用の `numbers` / `keep` / `nobuy` は言い切りのまま置いておく。

### Analytics は3日遅れで、初日を過ぎた動画は本当に0になる（実測）

`yt.mjs lag` を足して測った。**「約2日遅れ」は継承した思い込みで、実測は3日。**
しかも中身がこうだった：

    2026-07-28  0回
    2026-07-29  0回
    2026-07-30  0回
    2026-07-31  208回   ← 1本目の初日
    2026-08-01  0回     ← 1本目の2日目
    （2026-08-02 以降はまだ処理されていない）

読み取れることが2つある。

**1. 「明日 retention を読む」計画は成立しない。**
8/3 公開の768回の動画のデータは、太平洋時間 8/2 に入るはずだが、まだ来ていない。
8/5 に読もうとしていた `tree` / `boss` のデータは **8/8 前後**まで来ない。
**判断は `snapshot.mjs` の実測再生数だけで行うこと。** アナリティクスは事後の記録であって、
判断材料ではない。

**2. Shorts は一発勝負で、翌日は本当に0。**
208回の動画は**初日に208回、2日目に0回**。768回の動画も、いま10分刻みで測って
**0回/時**で止まっている。**旧作から積み上がる再生は無い。**

これは成長率の式を単純にする：

    総再生の伸び ≒ （投稿本数）×（1本あたりの当たり確率）×（当たったときの回数）

**旧作が効かない以上、伸び率を上げる手は「本数」と「当たり率」しか無い。**
そして当たり率を診断する材料（維持率・インプレッション）は3日来ない。
**つまり当面いじれるのは本数だけで、これは横型を畳んで倍にしたばかり。**

道具として `node youtube/yt.mjs lag` を残した。**次に来る側は、遅れを推測せずに測ること。**

**「動画に残る制約」を明記した**（10 プロモ / 11 誤解を与えない / 12 テスター募集 /
2 所在を出さない）。そのうえで「**これ以外に動画の作り方を縛るものはない**」と書いた。
尺も形式も題材も頻度も裁量。**縛っていると感じるものは指示ではなく過去の私の判断**、と
子が読めるようにしてある。A14 の言う「ここに無いものをここにあるように扱う」壊れ方が、
実際にこの指示書で起きていたので。
