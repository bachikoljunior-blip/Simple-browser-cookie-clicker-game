# 投稿の日誌

> **先に [`../../CLAUDE.md`](../../CLAUDE.md) の「YouTube 投稿の恒久指令」を読むこと。**
> 目標（総再生数の成長率の最大化）と、たった3つの制約はそこにある。この日誌が
> 持っているのは「なぜそうしたか」だけで、**何を目指しているかは持っていない。**
> 日誌の記述が指令と食い違ったら、指令が勝つ。

**追記だけ。過去の行を書き換えないこと。**

毎日の投稿は、常駐セッションに定期実行が撃ち込まれる形で回っています。そのセッションは
永遠には続きません。文脈が伸びれば要約されて薄れますし、いつか別のセッションに引き継ぐ
ことになります。

そのとき失われるのはコードではなく**判断の理由**です。何を試して効かなかったのか、
なぜその切り口をやめたのか、いつ何を変えたのか。`posted.json` は「何をいつ出したか」
しか持たず、アナリティクスは「どうなったか」しか持ちません。**「なぜそうしたか」を
持つ場所がここです。**

## 書き方

1回の投稿につき数行。長さより、書いてあること。**見出しに自分のセッションIDを
書いてください**（システムプロンプトの Claude-Session の URL にあります）。

```
## 2026-08-04  (session_01AbCdEf...)
- …
```

書く価値があるのは、**数字を見ても分からないこと**だけです。何を出したかは
`posted.json` に、成績はアナリティクスにあります。ここに要るのは、その数字を見て
何を考え、何を変え、何を変えなかったか。変えなかった理由のほうが、しばしば有用です。

**読むのは末尾10件ほどで足ります。** このファイルは伸び続けるので、全部読む必要は
ありません。古い記入が要るのは、いま触っている箇所の経緯を辿るときだけです。

## 毎回、必ず読み直すこと

**前回の記憶で動かないでください。** 同じセッションに撃ち込まれ続けるので、
「昨日これをやった」という感覚は残っています。その感覚は、日が経つほど薄れていく
一方で、薄れたことには気づけません。

だから毎回、このファイルと `posted.json` とアナリティクスを読み直してから判断して
ください。**1回の実行が独立していれば、このセッションは伸び続けても構いません。**
文脈が要約されて古い実行記録が消えても、失われるのはログの見た目であって、
判断材料ではないからです。

逆に言えば、読まずに記憶で動いた時点でこの前提が崩れます。乗り換えても直りません
——— 新しいセッションでも同じことをするので。壊れる経路はここ一本です。

## 引き継ぐとき

乗り換えは、伸びたからではなく **セッションが落ちたとき** か、**別の環境に移すとき**
にだけ必要になります。そのときは最後の記入を厚めにしてください。次に来る側は、この
ファイルと `posted.json` とアナリティクスしか持っていません。手順は
[`KICKOFF.md`](KICKOFF.md) にあります。

### 待機ループが自分自身を待っていた（セッション中ずっと）

撮影の完了を待つのにこう書いていた：

    until ! pgrep -f 'autopost.mjs' >/dev/null; do sleep 5; done

**この待機シェル自身のコマンド行に `autopost.mjs` が入っている**ので、`pgrep` が
自分に一致して**永久に終わらない**。12個たまっていた。撮影はとっくに終わっていて、
気づいていなかったのは待機側だけ。「まだ撮影中」と何度も報告したのはこれ。

正しい書き方は、`node` の起動に限定するか、パターンを自己一致しない形にする：

    until ! pgrep -f 'node .*autopost.*\.mjs' >/dev/null; do sleep 5; done
    # あるいは pgrep -f '[a]utopost\.mjs' （角括弧で自分に一致させない）

**そもそも待つ必要が薄い。** バックグラウンドで投げたコマンドは完了時に通知が
来るので、待機ループを別に立てるのは二重で、しかもこの罠を踏む。

### Cloud TTS は同じ入力でも尺が3割ぶれる（尺合わせを作り直した）

`keep` を撮っていて見つけた。**同じ文・同じ speakingRate** で、

    1回目  2.28秒
    2回目  3.07秒   ← 35%長い

open_jtalk は決定的だったので、尺合わせは「1回測って、1回だけ速度を直す」形で
足りていた。**Cloud TTS ではそれが破れる。** 1回目の計測から計算した補正は、
2回目の合成には当てはまらない。

**いちばん切れやすいのは最後の行**＝テスター募集の案内。動画の存在理由が、
たまたまその日ぶれた合成のせいで途中で消える経路だった。

直し方は「予測」から「収束」へ。**調整→測り直し→繰り返し**（最大3回、4%の余裕つき）。
上限は据え置き —— 上限は聞ける速さの限界であって、そもそも長すぎる行を救う速度は
無い。収まらない行は警告を出し、台本を短くする。

**教訓の形**: 決定的なものを非決定的なものに差し替えたとき、**その決定性に
乗っていた仕組みが黙って壊れる。** 声を差し替えたときに尺合わせを見直すべきだった。

### 「時間帯が効く」の対抗仮説：初期ブーストが尽きただけ

    順2  08-03 12:27   768    早い & 良い時間帯
    順3  08-03 21:00     1    遅い & 悪い時間帯

    順5  08-04 14:00     0
    順6  08-04 17:40     1

**同じデータが完全に説明できる。** 私が「09〜13時台が効く」と書いたのは、

- 初期ブーストモデル → **時刻をどういじっても無駄。** 配信は視聴維持で勝ち取るもので、

どちらも「最初期」ではない。

- 両方沈んだ → **初期ブーストモデル。** 時刻の話は全部捨てて、維持率と継続に寄せる
- 片方だけ → 形式（短縮版 vs 従来版）の差。時間帯モデルは弱まる

**この節を読まずに明日の数字を見ないこと。** 「12時台は2/2で強い」という
